# ADR 0003: Project-owned flow execution and review delivery

- **Status:** Accepted (2026-11-12)
- **Decision owner:** Project maintainer (approved option 2 in conversation on 2026-11-12)
- **Related work:** [Issue #1](https://github.com/DZunke/Falkenwarte/issues/1)
- **Scope:** How a Falkenwarte assignment resumes work and produces review evidence; not a replacement for Pi project trust or Git's review history.

## Context and evidence

The maintainer wants each project's `.falkenwarte/settings.json` to select either a local review package or a PR, with this repository using `pr`. An assignment must remain discoverable in that project's `.falkenwarte/` after Pi exits and support steering and a handoff. The closed prototype flow `0ddd9b87-0fac-4c99-b26d-5bcda59f6fcd` must not be reopened or reported as active. The existing prototype records milestones in Pi sessions and does not execute agents, create review packages or open PRs.

`pi-subagents@0.88.0` already has FleetView and saved async-workflow receipts. It may resume a workflow after owner exit when its saved launch and session remain available, but `stop` is terminal, not a resumable pause; replayed checks can be stale ([workflow documentation](../../../extensions/pi-personalities/docs/subagents.md)). `@agwab/pi-workflow@0.17.0` documents a workflow board, project-local `.pi/workflows/<run-id>/` engine records and `stop`/`resume`; loops cannot currently resume. It uses a **different** `@agwab/pi-subagent` engine, so personality bindings and activity attribution need independent verification ([upstream](https://github.com/AgwaB/pi-workflow/blob/main/docs/usage.md)). These are documented capabilities, not a successful restart test in Falkenwarte.

The user-approved preliminary boundary began with version 1 `review.delivery` (`local` or `pr`) and ignored `.falkenwarte/runs/<id>/run.json`. The later implementation accepts strictly checked optional `execution.autoStart` (default false) and `verification.commands` (reviewed argv arrays); this repository keeps automatic launch disabled because the upstream worker tool ceiling is broader than its spec. The flow record does **not** attest live agent state or replace the engine ledger. A second Pi process can reopen its view; it cannot resume a worker merely by reopening.

## Options

1. **Extend existing pi-subagents.** Keep its personas, receipts and FleetView. Add a Falkenwarte project run ledger, explicit interruption/handoff semantics, observed activity and review package. The engine still owns Pi session state and its stop cannot be relabelled pause. Least new dependency; substantial orchestration and UX code.
2. **Adopt pi-workflow as the execution backend.** Keep the Falkenwarte run reference under `.falkenwarte/runs/`, link it by exact engine run ID to `.pi/workflows/` in the same project, and use its board and stop/resume. Build an adapter for verified child identities, events and review output. This does not mean moving or symlinking upstream's engine records into `.falkenwarte/`. Adds another pinned engine and needs compatibility, platform and cold-restart tests; do not silently install it globally.
3. **Keep the current manual prototype.** Simple and low risk, but cannot meet pause/steer/handoff or mandatory review package expectations. Reject as a finished factory.

**Decision:** adopt option 2 as the execution backend. The maintainer wants a semi-automatic software factory: Waldemar accepts a ticket, runs a bounded workflow with specialist personalities, and ultimately hands back review evidence without requiring constant manual supervision. Separate tickets in separate worktrees must remain independent. Human steering, review and approval remain possible. The initial flow can be flat; more personalities, skills and stages can be introduced later. Adoption is an architectural decision, **not** a claim that the dependency, compatibility, recovery or PR path already works. Validate the backend in an isolated project/Pi home before enabling live launches.

## Boundaries and acceptance checks

- Tracked settings hold no credentials, commands, paths to a particular machine or arbitrary executable settings. Missing settings default to local; invalid settings fail closed. Ignored project run/review directories contain private runtime data and must not be staged. The target project's `AGENTS.md` and ADR archive remain authoritative.
- Reopening a Falkenwarte assignment restores its own metadata, **not** an agent process; worker status is unknown until an exact engine run ID is checked. A closed assignment is not automatically resurrected. A handoff names the run, observed receipts, unresolved decisions and next action without asserting unverified work.
- Local delivery creates an openable review package with scoped changes, test commands and results, real evidence files and explicit omissions; links must not escape the project or leak secrets. PR delivery requires reviewed branch scope, commits, push, PR URL and evidence-backed description; an open PR is not a merge or successful review. If delivery fails, report a blocked outcome instead of a successful `result`.
- Test stop vs pause, process exit, host restart, stale artifacts, concurrent writers, missing files and both review modes. Screenshot claims require actual files and an approved publication surface.

## Implementation evidence and remaining gates (2026-11-12)

- Linux/Node 24/Pi 1.5.2: the pinned npm 0.17.0 extension loaded alongside the Falkenwarte extension in an isolated Pi home. `/workflow validate spec-review` succeeded without launching workers. The portable installer then installed the exact pin on this machine after a conflict-free plan; owned-package tests and Pi extension command discovery passed. This is **not** a completed ticket, cold-restart or persona-in-worker test.
- The project run record accepts an exact engine `workflow_*` ID only from a tagged `workflow_run` tool call and a matching `.pi/workflows/<id>/run.json` in the same cwd. `reopen` remains a view operation. pi-workflow uses a separate child engine; the personality extension now recognizes its `PI_WORKFLOW_ROLE=worker` marker to prevent Waldemar's default identity leaking, but an actual specialist launch still needs verification.
- Brunhilde Nordwald's read-only architecture review identified five gates: separate flow/engine IDs, correct event attribution, real specialist identity, isolation between ticket worktrees, and a review package that cannot be replaced by a model's report. Her observations informed the guards above; no successful end-to-end execution was reported.
- An additional **real** isolated lifecycle check used a three-stage, read-only workflow in a disposable project outside this checkout with one short model worker, a bounded cooperative helper and a final worker. Its detached run `workflow_mwe1r5ed_104642` was observed running, `/workflow stop` marked three tasks interrupted, and `/workflow resume` from a new Pi CLI process reset and rescheduled them. `/workflow wait` then observed all three completed and a final `LIFECYCLE_RESUME_OK` artifact. This confirms stop/resume **after Pi process exit** for that run, not after host shutdown, not parallel ticket isolation, and not recovery of writing agents.
- A second disposable Git repository had two ticket branches/worktrees. Two read-only `falkenwarte-proof` runs completed independently (`workflow_mwe1vqg0_ce3404` and `workflow_mwe1vqe6_a71e85`). Each worktree contained only its own `.pi/workflows/<id>/run.json`; separate `.falkenwarte/runs/<flow-id>/` references and handoffs were created after observation, and reading the other worktree's engine ID failed. Neither a write-capable run nor automatic Factory launch was exercised.
- A further **disposable writing proof** in ticket A ran plan (`scout`) → implementation (explicitly generic `fw-implementer`, `worktreePolicy: off`) → read-only check (`scout`) and reached `completed`. `greeting.txt` in ticket A contained the requested exact bytes; ticket B remained clean. The check worker's separate worktree contained a snapshot of those candidate bytes and its output *reported* a match, but no captured tool-call or deterministic source-byte receipt proves that the worker actually read them. Pi-workflow validation warned that native `codemode`/MCP capabilities can widen even `readOnly` stages. This test spec is **not** a safe production review or a Falkenwarte personality mapping.
- A bounded `/factory review-draft` now materializes local HTML/JSON/Git-diff evidence only for a project-bound engine record reporting `completed`. It resolves a validated managed implementation task worktree (or explicitly labels a legacy direct writer), hashes actual tracked/untracked regular files, includes immutable untracked snapshots and copies only explicitly supplied, size-limited raster images into ignored `.falkenwarte/reviews/`. It refuses secret-looking filenames. It labels the absence of attested tests and semantic review plainly. This draft does **not** satisfy the required final review package or `review.delivery: pr`.
- An earlier flat `workflows/falkenwarte-flat/spec.json` used `worktreePolicy: auto` for its generic writer, then a trusted candidate-byte helper and a no-tool reviewer with a mandatory artifact read. In a disposable ticket-B worktree the actual run `workflow_mwe2oeh8_ab3d6a` completed all four stages. The writer's exact candidate bytes existed only in its managed task worktree; the original ticket worktree remained clean. The candidate control recorded SHA-256 and content, the reviewer read ledger recorded an untruncated `candidate.control` read, and an ignored HTML bundle captured the same untracked bytes. **That historical proof does not validate the revised in-place workflow.** It proves an artifact access, not semantic correctness, attested tests, a named Brunhilde/Albert identity, or a PR.
- The operator clarified ownership: **the factory must not create, delete, switch, merge, or backmerge worktrees.** The current flat spec and its default use `worktreePolicy: off`; implementation runs inside the checkout supplied by the operator, whether primary or linked. The trusted helper now requires the engine run and *all* its tasks to use that checkout. The preflight accepts a primary or detached checkout, requires a clean starting state and versioned spec/worker definitions, and does not launch a workflow yet. In-place capture cannot distinguish other processes' edits or commits; it must never be described as an isolated candidate proof. A fresh disposable **non-worktree** checkout completed all four stages as `workflow_mwe372kh_5bf662`: each task's engine worktree flag was `false`, `greeting.txt` held the requested bytes, and an ignored local HTML draft matched the candidate digest, reviewer read ledger and observed file hash (`verified-local`, advisory `needs_human`). This is a bounded in-place proof, not evidence that `/factory start` launches workers, that the reviewer has constrained native tools, or that a PR is safe. Notably the writer's effective tool record includes `codemode`, `tool_search`, and MCP tool access despite the spec's `read/bash/edit/write` list; enforce or explicitly accept the effective ceiling before unattended launch.
- Guarded `factory_launch` and optional `execution.autoStart` now wire `/factory start` to the exact in-place spec after a clean-checkout and active-engine preflight; this repository leaves automatic launch **off** because the effective worker tool record includes Codemode/MCP despite the spec's smaller list. A disposable RPC project with explicit `autoStart: true` actually launched and bound `workflow_mwe3w7rh_29e4ce` from `/factory start`, with all four tasks completing in the operator-provided checkout (`worktree.enabled: false`). Its ignored `final-v2` package recorded the matching candidate digest, reviewer read and one real host-run test command. The engine finished after its parent RPC process exited; the final package in this proof was built separately from the surviving record, **not** by a proven unattended post-exit watcher. The live board remains `/workflow`; closing a Factory view does not stop or resume it.
- `/factory review-final` now runs strictly configured, tracked host-owned test commands, hashes their bounded output, verifies the candidate and reviewer-read trace against the same bytes/diff before and after, and builds an ignored local `final-v<revision>` package only when checks pass. A session-local completion observer also attempts this for completed open auto-start runs; an offline Pi-RPC test verifies a fresh process finalizes an already-completed synthetic run from the project record. This does not prove a live daemon after Pi exits or host-reboot recovery. Unit fixtures show failed checks and changed bytes block delivery. The disposable RPC run's local package is real; a production ticket and independent semantic approval remain unverified.
- The revised flat spec now names a project-owned Brunhilde Nordwald reviewer agent. A separate disposable run `workflow_mwe48twc_e8d0df` completed with `review.main` loading that exact `.pi/agents/brunhilde-nordwald.md`, no task worktree, and an untruncated engine read-ledger entry for `candidate.control`. Her control artifact returned advisory `needs_human`. This verifies the selected worker prompt source and artifact access in that disposable run, not an extension-bound personality or independent approval of arbitrary production code.
- A PR path now requires read-only `/factory publish-plan OWNER/REPO DEFAULT-BASE` followed by exact same-session `/factory publish ... --confirm`. It checks local candidate and scope, verifies GitHub target/default branch, makes a scoped local commit and non-force push, then verifies PR head. It has read-only local checks and an offline end-to-end simulation with a local bare Git remote and fake `gh`, including scoped commit/push and verified PR-head response; **no authorized live GitHub push/PR proof** exists. `review.delivery: pr` alone never publishes.
- Still missing before claiming unattended production: enforce or explicitly approve the effective worker tool ceiling, validate the named specialist against a production ticket and real-ticket test receipts, test writing-run recovery across host interruption/reboot, and exercise a scoped PR with explicit operator authorization. A completed engine run or self-reported `result` phase is not acceptance.

## Consequences and reversibility

The project run ledger can be retained if the execution engine changes; a versioned adapter and exact engine ID avoid pretending a display ID is executable authority. Separate ignored runtime records protect private session data from Git, but a local handoff on another machine requires an explicit export, not an assumed sync. Option 2 can be removed without rewriting project knowledge; any migration of active engine records requires an explicit procedure. Unsupported platforms (native Windows in upstream 0.17.0), incompatible child identities or restart failures must surface as blocked, not silently switch to the old prototype or another backend. Review the package pin and its transitive dependencies before profile installation. The approval does not authorize closing Issue #1, merging a PR or reporting an unverified workflow as complete.
