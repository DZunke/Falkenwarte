# Profile ownership

The repository profile is intentionally narrower than a Pi agent directory. The script merges declared fields into Pi's existing files, so a machine can still have local packages, local skills and tools managed by other installers. This boundary matters most when you later publish the checkout.

| Repository source | Pi destination | Owned values |
| --- | --- | --- |
| [`config/settings.json`](../config/settings.json) | `settings.json` | Declared preference keys, including the automatic Atlavium theme and optional skill filters |
| [`config/packages.json`](../config/packages.json) | `settings.json` → `packages` | Local checkout packages plus exact remote package revisions |
| [`config/personalities.json`](../config/personalities.json) | `personalities.json` → `sources`, `default` | Paths to Markdown files inside the checkout and the startup personality |
| [`config/mcp.json`](../config/mcp.json) | `mcp.json` → named `mcpServers` | Reviewed server entries without credentials or machine-specific paths |
| [`extensions/pi-footer/config.json`](../extensions/pi-footer/config.json) | `extensions/pi-footer.json` | Entire footer layout at the extension's default config path |

`local` in `config/packages.json` contains only relative package directories inside the checkout, such as `themes/pi-atlavium`. The script calculates paths relative to Pi's agent directory for each machine. Remote packages are specified by a complete Git commit or exact npm version. Pi performs package installation from its own package manager; `update` calls `pi install` for exact remote pins before refreshing existing packages, because Pi's update command alone does not fetch a newly declared package. No extension source is copied into `~/.pi/agent/extensions/` by this script.

The `sources` list in `config/personalities.json` uses paths relative to the **repository root**. These become paths relative to Pi's agent directory when applied. Waldemar's profile is [`personalities/waldemar.md`](../personalities/waldemar.md), with optional historical background beside it. [`personalities/brunhilde-nordwald.md`](../personalities/brunhilde-nordwald.md) supplies the read-only architecture subagent's voice; [`personalities/albert-metzler.md`](../personalities/albert-metzler.md) supplies the domain explorer's voice. [`skills/pi-portable-skills/`](../skills/pi-portable-skills/) contains three original domain/story skills, ADR and GitHub workflow skills, and a browser skill backed by a locked npm CLI. [`extensions/pi-subscription-status/`](../extensions/pi-subscription-status/) fetches optional weekly Codex quota from the active Pi OAuth account, never from session token totals or a separate CLI login. [`extensions/pi-factory-flow/`](../extensions/pi-factory-flow/) provides a project-local task view, an opt-in guarded pi-workflow launch, local host-checked review packages and an operator-confirmed PR path; it never publishes from a preference alone. [ADR 0003](../.falkenwarte/knowledge/decisions/0003-project-flow-execution-and-review-delivery.md) selects the separately pinned `@agwab/pi-workflow@0.17.0` execution backend; its isolated in-place integration was exercised, but worker tool isolation, cross-host recovery and a live PR publication still need verification. The dependency requires Node >=22.19 on Linux/macOS (Windows through WSL2), so `config/packages.json.platforms` excludes it on native Windows without removing unrelated packages. On a new installation, Waldemar is the default for each main Pi session and appears in its footer. Subagent children deliberately do not inherit his identity. Use `/personality default` to pick another loaded personality locally, then explicitly run `capture --dry-run` and `capture` to make that choice portable. A default sourced only from the machine-local personality directory cannot be captured until its reviewed Markdown is placed in this checkout and added to `sources`. A `--personality` flag or `PI_PERSONALITY` overrides the saved default for that process.

## Add settings or integrations

For a safe new standard setting, add its key and value to `config/settings.json`, run `plan`, then apply. Alternatively set it in Pi and run `capture --setting NAME` after reviewing its contents. `capture` does not automatically copy unknown fields. The script rejects obvious secrets, absolute paths and URLs in settings. The checkout's seven skills install as a local Pi package; references to other optional skills still require their own installation. `.falkenwarte/knowledge/` is a Git-reviewed store of **this project's** decisions and domain evidence, not an applied Pi resource or a credential store. For a different project, initialize its own directory explicitly with [`scripts/falkenwarte-project.mjs`](../scripts/falkenwarte-project.mjs); preserve an existing ADR convention. Personality `skills.allow` and `skills.deny` lists filter the advertised prompt skills and direct `/skill:name` input, not resource discovery, command autocomplete, or tool permissions. See [format and limits](../extensions/pi-personalities/docs/format-and-sources.md).

Add an MCP server to `config/mcp.json` only if it is either an HTTPS endpoint without a query string or a bare executable name with an argument array. Install that executable yourself. The existing `codegraph` command and Sentry endpoint work only when their separate dependencies and credentials are available on that machine. More elaborate local MCP setups belong in the machine's own file until you have a safe portable design.

Local packages load their code directly from the checkout. After a third-party upgrade, `update` loads them in a Pi RPC smoke test and runs their `test` and `smoke` scripts. If an owned package declares runtime `dependencies`, commit its `package-lock.json`; `update` then runs `npm ci --omit=peer --ignore-scripts` before the tests. A package needing native install scripts requires a separate, reviewed installation step. The browser CLI is smoke-tested after `npm ci`; its Chromium runtime is downloaded separately by `node skills/pi-portable-skills/scripts/browser.mjs install` when needed. Pi packages have separate module roots: don't assume `pi-footer` can be imported from another package just because Pi installed it. The personality indicator uses Pi's published extension status instead. Declare Pi-provided APIs as peer dependencies, not runtime dependencies. Versioned `config/packages.json.platforms` keys identify a remote package without its revision so pin updates retain the platform restriction; the update/install path must filter packages by the current host platform.

The Herdr-managed extension currently found in `~/.pi/agent/extensions/` is intentionally not copied: Herdr says its installer owns that file and may replace it. The old `~/.pi/waldemar/` package is likewise not part of this profile; installing it in parallel could load duplicate themes. To package a new *owned* extension, put it in a reviewed local Pi package and add that directory to `config/packages.json`.

For operating commands see [bootstrap](bootstrap.md), [update and capture](updates-and-capture.md), [footer configuration](footer.md), and [subagent integration](../extensions/pi-personalities/docs/subagents.md). Update this map when adding another managed profile file.
