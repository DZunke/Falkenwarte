# Workshop a GitHub Issue with the team

This is a **conversation first**, not a command that creates an Issue on invocation. Discuss the idea in the user's language, but draft the Issue title and body in English by default; follow explicit user instructions and established repository conventions when they differ. Waldemar moderates, the user decides what matters, Albert Metzler tests domain language and examples, and Brunhilde Nordwald challenges architecture, scope and risks. The Issue is the agreed work item, not a substitute for an ADR. Use [the draft shape](assets/issue-draft.md) as a checklist, not a form that invents answers. The parent session owns the draft, GitHub mutation and final link.

1. **Clarify the destination and seed.** Ask what outcome the user wants and which repository should own it. Read that project's `AGENTS.md` and existing Issue conventions. Confirm the actual `OWNER/REPO` using its remote and `gh repo view OWNER/REPO --json nameWithOwner,url` when available; never assume this portable profile is the target. If the repository or access is unclear, brainstorm locally and pause before publication. Do not create a worktree or modify code to file an Issue.
2. **Brainstorm together.** Ask a few focused questions at a time: who benefits, what happens today, desired behavior, one concrete acceptance example, exclusions and important unknowns. Present plausible options or a smallest useful increment rather than turning assumptions into requirements. After there is enough context, delegate **read-only, bounded** questions to the relevant specialists using pi-subagents: Albert for contested business terms, exceptions or user journeys; Brunhilde for architectural consequences, interfaces, dependencies and failure modes. For an issue spanning both seams, ask them independently, then synthesize their observations and any disagreement for the user. Do not summon an irrelevant specialist for ceremony or let a child publish. Follow the `pi-subagents` skill for actual delegation; Waldemar remains the orchestrator.
3. **Check existing work.** Read the [`github-issues-projects` skill](../github-issues-projects/SKILL.md) and its [gh reference](../github-issues-projects/references/commands.md) before using GitHub. Search the **confirmed repository** for related open and closed Issues (for example `gh issue list --repo OWNER/REPO --state all --search "<key terms>" --limit 100 --json number,title,state,url`). Inspect likely matches with `gh issue view`. A bounded search cannot prove no duplicate exists; show likely overlaps and ask whether to extend an existing Issue instead. Do not access Projects or request `read:project` just to create an Issue.
4. **Agree on the exact draft.** Assemble a concise title and body with context, outcome, acceptance examples, scope/non-goals, risks or open questions, and links to verified local ADRs or related Issues where appropriate. Mark proposals and unknowns honestly. If the request entails a consequential architecture or domain decision, use `adr-decision` to seek approval before presenting an implementation choice as settled. Show the user the **exact target repository, title and full body**. Ask explicitly whether to create *this* Issue there. A request to brainstorm, a skill invocation or an earlier generic approval is not permission to publish an unreviewed draft. Labels, assignees, Projects and comments are separate actions requiring their own scope and authorization.
5. **Create once after approval.** Check `gh --version` and authentication (`gh auth status --active`, never reveal tokens). Save the approved body to a private temporary file **outside the repository**; do not put credentials or private data in the Issue. Execute `gh issue create --repo OWNER/REPO --title "<approved title>" --body-file <temporary-file>`, then remove the temporary file. Do not auto-retry if the call fails or its result is ambiguous: an Issue may already exist. Read back the returned URL with `gh issue view <exact-url> --repo OWNER/REPO --json number,title,body,state,url` and check the repository, title and body against the approved draft. If verification fails after creation, report the possible Issue URL and partial state rather than filing another.
6. **Hand back the receipt.** Return the verified Issue link, number and repository. Briefly note any unresolved questions the approved Issue records. If publication was declined or blocked, return the agreed draft without claiming an Issue exists. Do not auto-start `/factory`, advance a GitHub Project, or change Issue status as a side effect.

Example entry: `/skill:team-issue-workshop We need a clearer recovery story for interrupted ticket runs.` The first response should clarify outcome and target, not call `gh issue create`. If the user later approves a final draft, the last response includes the verified Issue URL.
